Overview & Philosophy

In ln-ashlar, search is implemented using the Two-Host / Attribute Bridge Architecture. It splits the search workflow into two decoupled roles:

  • The Control (data-ln-search-for="targetId"): Sits on the input element or wrapper. It manages keystroke capture, debounce delays (default 500ms), clear-button interactions, and writes the search term into the target's attribute.
  • The State Host (data-ln-search="term"): Sits on the target container (list, table, section). It owns the search term as the Single Source of Truth, detects attribute changes via MutationObserver, performs reverse synchronization to controls, dispatches ln-search:change, and runs tokenized AND matching.

The Attribute Bridge Contract

Controls never hold direct JS memory references to targets. Writing or editing data-ln-search="term" on a target element (including live edits in DevTools Inspector) immediately updates the target state, reflects the query back into all matching [data-ln-search-for="targetId"] inputs, and dispatches the cancelable ln-search:change event.

Orthogonal Integration Lifecycles

  1. The Passive Path (Zero-JS DOM Filtering): When no custom event listener calls preventDefault(), the target runs an order-independent tokenized AND search over child elements (or deep items via data-ln-search-items), tagging non-matching items with data-ln-search-hide="true". Items with data-ln-search-exclude are exempt.
  2. The Active Path (Table & Coordinator Integration): Active components (such as ln-table or custom coordinators) intercept ln-search:change, call e.preventDefault() to deactivate default DOM hiding, and execute their own in-memory or remote query pipelines.
  3. The Boot Seeding: Authored or deep-linked data-ln-search="value" on targets, as well as browser form restoration on inputs, are seeded safely through queueBoot so consumer listeners finish initialization first.

For the full guide see the ln-search README and the architecture reference.

Authoring Rule — Required Chrome

Every search/filter input MUST use the full .search chrome (icon + clear button). The minimal-markup examples further down on this page isolate specific JS behaviors and are NOT authoring templates.

Anatomy

The canonical (required) form places data-ln-search-for="targetId" on the <input> and defines data-ln-search="" on the target container:

  <input type="search" placeholder="Search..." data-ln-search-for="my-list" data-ln-search-debounce="0">
  <button type="button" data-ln-search-clear aria-label="Clear search">
    <svg class="ln-icon" aria-hidden="true"><use href="#ln-icon-x"></use></svg>
  </button>

    <li>Argentina</li>
    <li>Brazil</li>
    <li data-ln-search-exclude>Exempt Item (Always Visible)</li>
</ul>

The chrome (border, focus ring, icon spacing, clear-button visibility) comes from @mixin search in scss/components/_form.scss.

Default vs. deep targeting

The default behavior iterates direct children of the target. For nested structures (like table rows or grouped icon cells), add data-ln-search-items="selector" on the target element; the component then runs target.querySelectorAll(selector) on every search.

Exemptions and Subtree Exclusion

Use data-ln-search-exclude to control search boundaries: on an item root, the item is completely exempt from filtering and remains visible; on a descendant element (e.g. action buttons or badges), that subtree is omitted from text matching.

Composition — ln-table integration

When data-ln-search-for points to an ln-table element with data-ln-search="", ln-table intercepts ln-search:change, calls preventDefault(), and filters records in-memory:

<input type="search" placeholder="Search..." data-ln-search-for="my-table">

<section id="my-table" data-ln-table data-ln-search="">
    <table>...</table>
</section>

See the Table and Table Filter demos for live integrations.

Composition — independence from ln-filter

ln-search and ln-filter operate on the same target without coordinating. Each manages its own hide attribute; an item is visible iff both are absent:

[data-ln-search-hide],
[data-ln-filter-hide] {
    display: none !important;
}

The CSS rules ship in the library defaults. Neither component knows about the other.

API

// Control instance on the input
const controlEl = document.querySelector('[data-ln-search-for]');
controlEl.lnSearchControl.targetId;          // string
controlEl.lnSearchControl.input;             // HTMLInputElement
controlEl.lnSearchControl.debounceTime;      // number (ms)
controlEl.lnSearchControl.destroy();

// State instance on the target
const targetEl = document.querySelector('[data-ln-search]');
targetEl.lnSearch.term;                      // string (current raw term)
targetEl.lnSearch.destroy();

To programmatically set search term, simply set the attribute on the target (Single Source of Truth) or write to the input:

// Recommended: Attribute Bridge (Inspector or Script)
document.getElementById('demo-list').setAttribute('data-ln-search', 'argentina');

Common mistakes

1. Putting data-ln-search="targetId" on the input

data-ln-search is the state attribute on the target. The input control must use data-ln-search-for="targetId".

2. Omitting data-ln-search-debounce="0" for local DOM search

For instant filtering of static DOM items without network calls, always set data-ln-search-debounce="0" to remove the default 500ms throttle delay.

3. Listening for input directly to bypass debounce

Always listen for ln-search:change on the target element; you get automatic debouncing, normalized terms, and token arrays.

Overview & Architecture

For datasets too large to cache entirely client-side, ln-table provides a high-performance **SSR Hydration & Windowed Sync** pipeline: an instant paint from server-rendered rows, followed by a bounded sliding-window cache that fetches pages from the server as the user scrolls.

Lifecycle Mechanics

1. **Instant SSR Paint**: The table loads with a fast pre-rendered subset of rows (e.g. 100 rows printed inside <tbody> by the server, matching the server-declared data-ln-table-count grand total). 2. **Local Hydration**: The JS layer instantly parses these pre-rendered rows on load, enabling immediate client-side sort and search over the hydrated subset. 3. **Windowed Sync Configuration**: - data-ln-table-window="1000": Caps resident cache memory at 1,000 rows. - data-ln-table-window-page="200": Configures page/chunk fetch size (`limit=200`). - data-ln-table-window-threshold="25": Configures prefetch trigger margin (`25` rows before reaching unloaded page boundary). - data-ln-table-count="10000": Declares the server grand total. As the user scrolls, the table requests page-aligned chunks from the PHP backend API (e.g. `offset=200&limit=200`) and evicts LRU rows to stay under the cap. No initial fetch on load: the first 100 SSR rows seed the resident window directly. 4. **Continuous Scroll**: Rows outside the resident window render as blank placeholders until their page arrives; there are no pagination controls — scrolling stays continuous over the full server-side dataset.

Remote Full-Text Search Integration

When searching, the table first filters local cached items for instant visual response, and then dispatches the search term to the PHP backend. The PHP API runs a full-text search across title, department, owner, and tags properties, returning matches from the entire 10k database.

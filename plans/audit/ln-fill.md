# Аудит — ln-fill

2026-09-11 · Опсег: `src/ln-fill.js` (87), `README.md` (199), schema · Итерација 22/50

## Вердикт

87 линии со најдобро образложената архитектонска одлука во репото — README-от
објаснува **зошто** е диспечер функција наместо document broadcast. Но втората
влезна точка на компонентата (`ln-fill:request`) нема ниту еден ред договор, а
`data-ln-fill-store` е резервиран за иднина што сè уште не постои.

## Што е добро

**Секцијата „Why a dispatcher function, not a document broadcast" (README:21-43)**
е реткост: одлуката е изнесена како избор меѓу две опции, со причината зошто
broadcast-от не може да го изрази случајот — еден запис што полни форма **и** повеќе
display fillable-и, без производителот да знае ниту едно id. Тоа е документација што
одговара на „зошто", не на „што".

**`data-ln-fill-id` двојно служи, и тоа е load-bearing.** Суфиксот `Id` минува низ
`_recordFrom` (`:19-21`) и станува `record.id` — токму полето што
`ln-form._applyActionMode` (`ln-form.js:71`) го бара за да префрли форма во edit
режим. Значи еден атрибут го носи и адресирањето и RESTful рутирањето.

**Двојното полнење е спречено, со запишана причина** (`:47-51`): hash-врзан
anchor се прескокнува затоа што промената на hash-от ќе го активира
`ln-modal:open`, а координаторот потоа ќе побара fill преку `ln-fill:request`.
Коментарот ја именува целата патека.

**Не краде `preventDefault()`** (`:53-54`) — истиот клик може да го обработува и
`[data-ln-modal-for]`. Компонентата свесно се воздржува и го кажува тоа.

**`CSS.escape` со feature-detect** (`:27`) пред интерполација во селектор —
единствената компонента досега што го прави тоа.

**Detail Guard** на `ln-fill:request` (`:67`).

## Наоди

### 🟠 FI1 — Резервиран атрибут за иднина што не постои

**Каде:** `:8-11` и `README.md:90`

```js
// data-ln-fill-store is RESERVED for a future store-source seam.
// When implemented, the click handler will look up a record from a named
// store (e.g. window.lnCore stores) instead of reading flat data-* attributes.
const RESERVED = { lnFillForm: true, lnFillStore: true };
```

`lnFillStore` чува од атрибут што:
- не постои во ниту еден фајл на библиотеката
- нема консумент
- нема имплементација

DOCTRINE §2 („Definition of Done") вели дека функција постои само ако денес ја вика
DOM школката. Овде и кодот и коментарот се чисто шпекулативни.

README:90 го повторува во договорната секција:

> `store` (`data-ln-fill-store`) — reserved for a **future** store-source seam

Тоа е и втор прекршок — доковите се пишуваат во финална состојба, без временско
скеле („future", „when implemented"). Ист облик како SYS-5 („v1"), но овде е
опишана функција што воопшто не постои, не ограничување на постоечка.

(`lnFillForm` во истиот објект е легитимен — тој атрибут постои и мора да не влезе
во записот.)

### 🟠 FI2 — Втората влезна точка нема договор

**Каде:** `:65-82`

Компонентата има **два** влеза:

| влез | документиран? |
|---|---|
| `click` на `[data-ln-fill-form]` (`:41-63`) | ✅ целосно — §2 Blueprint, §3 Attribute Reference, §4, §5 |
| `ln-fill:request` на `document` (`:65-82`) | ❌ една спомената реченица (README:115) |

README:115 го спомнува само како нешто што **координаторот испраќа**, во контекст на
спречување двојно полнење. Никаде не е запишано дека `ln-fill` **слуша** за него,
ниту:

- дека `detail.id` е клучот што се бара
- дека `detail.id == null` значи „исчисти го целниот контејнер" (`:72-75`)
- дека изворот се бара по `[data-ln-fill-id="<id>"]`
- дека `e.target` е контејнерот што се полни

Тоа е патеката што ја носи целата modal + hash интеграција. README нема ни секција
за настани (`### Emitted` / `### Received`), што секоја друга компонента ја има.

### 🟠 FI3 — Пребарувањето на извор е низ цел документ, со тивок fallback

**Каде:** `:26-39`

```js
const candidates = document.querySelectorAll('[data-ln-fill-id="' + escaped + '"]');
if (candidates.length === 0) return null;
for (…) { /* претпочитај извор чија форма е ВНАТРЕ во container */ }
return candidates[0];
```

Опсегот е `document`, не `container`. Кога два независни дела од страницата користат
ист `data-ln-fill-id` — на пр. две табели што прикажуваат различни ентитети со
преклопувачки нумерички id-а — селекцијата паѓа на:

1. првиот кандидат чиј `data-ln-fill-form` резолвира во форма **внатре** во
   контејнерот (`:35`) — точно кога тој атрибут е поставен;
2. инаку **`candidates[0]`** (`:38`) — првиот во документен ред, кој може да припаѓа
   на сосема друг список.

Вториот пат нема ни предупредување ни dev афорданс. Формата се полни со **погрешен
запис**, тивко.

**Достижност:** две листи на иста страница со нумерички id-а од различни табели —
обичен случај во админ панел (`/users/42` и `/orders/42`).

### 🟠 FI4 — Уште една послаба копија на `shouldIgnoreClick`

```js
if (e.ctrlKey || e.metaKey || e.button === 1) return;
```

Недостасуваат `shiftKey`, `altKey` и секое не-примарно копче освен средното.

### 🟡 FI5 — Празен `import` како плумбинг за редослед на вчитување

**Каде:** `:1`

```js
import { } from '../../ln-core';
```

Нула врзувања. Постои затоа што компонентата го користи
`window.lnCore.lnFill` (`:62`, `:73`, `:81`), кој се доделува при вчитување на
модулот `ln-core` (`helpers.js:1037`) — значи увозот гарантира редослед, не симбол.

Тоа е легитимна техника и README:16 го документира глобалот како **договорен**
примитив (*„The underlying primitive is `window.lnCore.lnFill(container, record)`"*).
Наодот е дека **во кодот нема ниту еден коментар** што го објаснува — а празен
увоз е точно она што следниот читател ќе го избрише како мртов.

Секој друг коментар во овој фајл објаснува зошто; овој ред, што најмногу го бара, го
нема.

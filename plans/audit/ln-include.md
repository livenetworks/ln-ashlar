# Аудит — ln-include

2026-09-10 · Опсег: `src/ln-include.js` (103), `README.md` (73), schema · Итерација 8/50

## Вердикт

Единствената компонента досега што го прави bail патот **правилно** — и истовремено
единствената што може трајно да ја замрзне иницијализацијата на целата страница,
бидејќи `fetch` нема ни timeout ни abort.

## Што е добро

**`this.dom = dom` доаѓа ПРЕД bail-от.** `:15` доделува, `:21` bail-ира. Затоа
`destroy()` работи и на инстанца создадена преку празен URL. Тоа е точно
спротивното од `ln-autoresize` AR1 и `ln-slug` S1, кои bail-ираат пред доделувањето
и пукаат. Истиот облик, точен редослед — ова е шаблонот што другите две го немаат.

**Ослободувањето на портата е покриено од три страни:** успех (`:65`), грешка
(`:78`), и `destroy()` (`:94`), сите зад `_held` знаменце што спречува двојно
декрементирање. README-от од `ln-core` покажува пример со **само** `.then` — овде
кодот е построг од сопствената документација.

**Кешот на одбиено ветување се празни во моментот на одбивање** (`:43`), па
подоцна создаден host повторно се обидува наместо да падне веднаш врз застаран
reject. Тоа е запишано во Internals точка 4.

**Пресметан избор на parser:** `document.createElement('template')` + `innerHTML`
(`:53-54`) наместо `innerHTML` врз `div`, за да преживеат `<tr>`, `<td>`, `<option>`
— кои `div.innerHTML` ги отфрла. Коментарот на `:52` ја кажува причината.

**Pitfalls секцијата е искрена** — „late-entering hosts are ungated", „standalone
bundle script order", „content vs registry". Ретко се пишува што компонентата **не**
покрива.

## Наоди

### 🔴 I1 — `fetch` без timeout замрзнува boot на цела страница

**Каде:** `:35` — `promise = fetch(url)`

Нема `AbortController`, нема timeout, нема watchdog. Ако серверот прифати
конекција и никогаш не одговори, ветувањето **никогаш не се решава**:

1. `holdInit()` (`:26`) го крева `window.lnCore._bootHolds` на 1.
2. Ниту `.then` (`:49`) ниту `.catch` (`:67`) не се извршуваат.
3. `_held` останува `true`, `releaseInit()` никогаш не се вика.
4. `registerComponent`-овиот `boot()` за **секоја друга компонента** гледа
   `pendingCount() > 0` и оди во `queueBoot`.
5. `_bootQueue` никогаш не се празни.

**Резултат:** ниту една компонента на страницата не се иницијализира. Без грешка,
без предупредување, без визуелен сигнал. Само мртва страница.

**Достижност:** висока за реален деплој. Не бара грешка во кодот — доволен е спор
или заглавен сервер за еден партиал.

**Врска:** ова е достижниот крај на `ln-core` R11 (портата нема watchdog). README-то
тука вети *„Boot Gating (No race conditions)"* без да го спомне режимот на откажување.

### 🟠 I2 — `destroy()` не прекинува работа во лет

**Каде:** `:87-98`

DOCTRINE §5 „Destroyed Component Invariant" бара async компонента при `destroy()`
да ја прекине работата во лет. Овде `destroy()` само поставува `_destroyed = true`
и ја ослободува портата — `fetch`-от продолжува до крај, парсира одговор и го
отфрла на `:50` / `:68`.

За еден партиал тоа е неколку изгубени килобајти. Во SPA каде рутата се менува
брзо, секоја напуштена рута остава своја врска жива.

`AbortController` не се појавува никаде во фајлот.

### 🟠 I3 — Сиров `console.error`

**Каде:** `:70`

`ln-core`-овата конзолна порта (`helpers.js:1-19`) ја закрпува само `console.warn`.
`console.error` минува непречистено во продукција — истата класа како `ln-core` R8.

### 🟡 I4 — `destroy()` не постои во README

README нема ниту еден ред за `destroy()`, ниту за `_held` / `_destroyed`
семантиката. Компонентата има јавен `destroy` на прототипот (`:87`) што учествува
во ослободувањето на глобалната boot порта — тоа е најмалку локална одлука во целата
компонента, и е недокументирано.

### 🔵 I5 — Успешниот кеш никогаш не се поништува

`_fetchCache` (`:10`) го чува решеното ветување трајно. Во долгоживеачка SPA,
партиал што се менува на серверот никогаш не се превчитува. Одбиените се бришат
(`:43`), успешните не.

# Аудит — ln-api-queue

2026-09-11 · Опсег: `src/ln-api-queue.js` (336), `src/queue-storage.js` (459), `README.md` (221), schema · Итерација 35/50

## Вердикт

Најдобро проектираната компонента во библиотеката за тестирање — целата логика за
конкурентност живее во две **чисти извезени функции**, а складот прима
`indexedDB`, `IDBKeyRange`, `now` и `uuid` како инјектирани зависности. Но кога
IndexedDB воопшто го нема, `enqueue` тивко ја отфрла мутацијата и не испраќа ниту еден
настан — точно гаранцијата што README-то изречно ја дава.

## Што е добро

**Логиката за конкурентност е чиста и извезена.** `claimQueueHeads`
(`queue-storage.js:32-64`) и `remapQueueEntries` (`:66-88`) се обични функции над низи
— групирање по `chainKey`, сортирање по `seq`, проверка на закуп, доделување. Ниту
една не допира IndexedDB. Значи најделикатниот дел од компонентата — кој запис се
презема и кога — може да се тестира без прелистувач.

**Складот е целосна инјекција на зависности.** `QueueStorage` конструкторот
(`queue-storage.js:91-100`):

```js
this.indexedDB = options.indexedDB || globalThis.indexedDB;
this.keyRange   = options.IDBKeyRange || globalThis.IDBKeyRange;
this.dbName     = options.dbName || DEFAULT_DB_NAME;
this.now        = options.now || (() => Date.now());
this.uuid       = options.uuid || (() => crypto.randomUUID());
```

Четири инјектибилни точки, вклучувајќи го часовникот и генераторот на идентификатори.
Ниту една друга компонента во репото не оди толку далеку — и тоа е точно она што
backoff-от и истекот на закуп го прават проверлив без чекање од пет минути.

**Закупот е доделен во иста трансакција во која е прочитан.** `claimReady`
(`:230-252`) чита, пресметува и запишува во еден `readwrite` tx. README:117-123 ја
објаснува последицата — повеќе табови не можат да го земат истиот запис, зашто
IndexedDB ги серијализира трансакциите врз ист store.

**Опоравувањето од истечен закуп е вграден механизам, не заборавена гранка.**
`claimQueueHeads:47-49` — кога главата е `inflight` со жив закуп, наместо да се
прескокне тивко, се внесува во `wakeups` со точното време на истекот. `_drain`
(`:117-119`) од тоа прави `setTimeout`. Значи таб што паднал среде праќање се опоравува
сам по 60 секунди.

**Мигрирачката патека од v1 е напишана и објаснета** (`queue-storage.js:213-220`):
кога `seq` бројачот за опсег го нема, се иницијализира **над** најголемиот веќе
запишан `seq`. Коментарот ја кажува причината. Ретка грижа за податоци што веќе
постојат кај корисник.

**`onversionchange` → `close()`** (`queue-storage.js:131`) — друг таб што ја надградува
базата не го блокира; овој таб се повлекува.

**Секој метод на складот се деградира на неутрална вредност кога нема база** —
`[]`, `null`, `0`, `false`, `{entries:[],wakeups:[]}` (`:158`, `:171`, `:232`, `:267`,
`:332`, `:355`, `:385`, `:437`). Ниту еден не фрла. (Последицата од таа тишина е QU1.)

**`idempotencyKey: entry.entryId`** (`:130`) — стабилен низ секој повторен обид, зашто
`entryId` е примарниот клуч што не се менува. Точниот избор, и README:98 го именува.

**`destroy()` е целосен** — девет слушачи на елементот, `online` слушачот на
`window`, сите тајмери, плус `:destroyed` (`:304-324`).

**Компонентата е навистина connector-blind и id-blind**, и README:169-171 го изјавува.
Нула `fetch`, нула URL, нула увоз од друга компонента.

### 🔴 QU1 — Кога IndexedDB го нема, мутацијата се губи тивко

**Каде:** `queue-storage.js:104` → `:171` → `src/ln-api-queue.js:150` наспроти `README.md:106`


```js
// queue-storage.js:170-171

	return this.open().then(db => {
		if (!db) return null;
```

```js
// ln-api-queue.js:148-150
return _storage.enqueue(self.scope, e.detail || {})
	.then(entry => {
		if (!entry) return;        // ← крајот на патеката
```

Нема `ln-api-queue:enqueued`. Нема `ln-api-queue:error`. Нема `pending-count`. Нема
`ln-api-queue:send`. Мутацијата што корисникот ја направил — создавање запис, измена,
бришење — исчезнува без ниту еден сигнал кон координаторот.

README:106 ја дава спротивната гаранција, збор по збор:

> `ln-api-queue:error` | `{ operation, entryId?, error }` | IndexedDB or queue
> orchestration failed **without silently discarding the entry**.

Единствениот сигнал е едно предупредување при boot (`:49`):
`console.warn('[ln-api-queue] IndexedDB not available — queue disabled')` — со
`[ln-` префикс, значи **зад дебаг гејтот**, значи невидливо во продукција.

**Разграничување:** ова е само патеката каде IndexedDB API-то воопшто го нема. Кога
`open()` **се одбива** (квота, блокирана надградба, приватен режим што фрла), одбивањето
се пропагира низ `enqueue` до `.catch` на `:160` и `ln-api-queue:error` се испраќа
точно како што README-то ветува ✅. Значи гаранцијата важи за отказите и паѓа за
отсуството.

**Достижност:** `window.indexedDB === undefined` — вградени WebView-и со исклучен
склад, iframe-ови под партиционирање на трета страна, и режими за приватност што го
кријат API-то наместо да фрлат. Тоа е точно популацијата за која офлајн редица постои.

### 🟠 QU2 — `nack` со непозната причина остава запис заклучен и во бесконечна јамка

**Каде:** `queue-storage.js:276-313`

```js
request.onsuccess = () => {
	const entry = request.result;
	if (!entry || entry.scope !== scope) return;

	if (reason === 'drop') { … return; }

	clearLease(entry);                 // ← само во меморија
	entry.updatedAt = this.now();      // ← само во меморија

	if (reason === 'auth')  { … outbox.put(entry); … return; }
	if (reason === 'retry') { … outbox.put(entry); … }
	// ← ниту една друга причина не стигнува до outbox.put
};
```

За причина што не е `'drop'`, `'auth'` или `'retry'` — вклучувајќи **отсутна**
(`detail.reason === undefined`) — `clearLease` го менува само локалниот објект.
`outbox.put(entry)` никогаш не се повикува, па запишаниот запис го задржува она што
`claimQueueHeads` го поставило: `status: 'inflight'`, `leaseOwner`, и
`leaseUntil = now + 60000`.

`result` останува `null`, па `_onNack` излегува на `:184` (`if (!result) return;`) —
без настан, без `pending-count`, без закажување.

Последицата не е застој туку **циклус**:

1. Синџирот е блокиран 60 секунди (жив закуп).
2. `claimQueueHeads:47` внесува `wakeup` на времето на истекот, па `_drain` закажува
   тајмер.
3. По истекот записот се презема **повторно** и се испраќа повторно.
4. `attempts` никогаш не е зголемен — значи прагот од 8 обиди никогаш не се достигнува,
   `status: 'failed'` никогаш не настапува, `ln-api-queue:failed` никогаш не се
   испраќа.

Истата мутација се праќа на серверот на секои 60 секунди, засекогаш, тивко.

**Достижност:** испорачаниот `ln-data-coordinator` праќа точно три причини —
`'auth'` (`:654`), `'retry'` (`:663`), `'drop'` (`:689`) — значи оваа патека **не е
достижна преку него**. Но целиот интеграциски образец на README-то (`:175-198`) е
координатор што консументот сам го пишува, и README:86 е единственото место каде
трите дозволени вредности се наведени. Изостанат `reason` е најлесниот промашај, и не
постои ниту дев афорданс ниту `ln-api-queue:error` што би го открил.

### 🟠 QU3 — Индексот `by_scope_chain` се создава и одржува, а никогаш не се чита

**Каде:** `queue-storage.js:117-119` наспроти `README.md:51`

```js
if (!outbox.indexNames.contains('by_scope_chain')) {
	outbox.createIndex('by_scope_chain', ['scope', 'chainKey'], { unique: false });
}
```

Grep низ `components/*/src/**` за `by_scope_chain`: **две појави**, обете се самото
создавање. Секое читање во складот оди преку `by_scope_seq` — `allForScope:161`,
`enqueue:215`, `claimReady:237`, `_remapTransaction:336`, `resetFailed:359`,
`clear:418`. Главата по синџир се наоѓа **во меморија**, со групирање во
`claimQueueHeads:37-44`.

README:51 тврди дека индексот има работа:

> `by_scope_chain` (`[scope, chainKey]`), `by_scope_seq` (`[scope, seq]`) … —
> **`by_scope_chain` is used to find the head entry per chain.**

Не е. Цената не е нула: IndexedDB го одржува на секој `put`, а `put` се случува при
секое ставање во редица, секое преземање, секој nack и секое пре-клучување.

Дополнително, вредностите со кои се полни се сомнителни: `chainKey` доаѓа директно од
`detail.chainKey` (`:185`) без валидација, а запис со `undefined` `chainKey` воопшто
не влегува во композитниот индекс.

`DOCTRINE.md` §2, **No Speculative Code**: *„Uncalled or dead functions are strictly
forbidden."*

### 🟡 QU5 — `_drain()` за време на активно празнење не закажува продолжение

**Каде:** `:113` наспроти `:259-260`

```js
if (self._drainPromise) return self._drainPromise;
```

Четири патеки викаат `_drain()` директно по промена во складот — `_onEnqueue:157`,
`_onAck:170`, `_onNack:204`, `_onResolveCreate:225`. Ако празнење веќе трча, сите
четири го добиваат **тековното** ветување и не предизвикуваат ново читање.

Само `_onDrain` (`:256-264`) го знае тоа и се врзува правилно:

```js
const activeDrain = self._drainPromise;
return activeDrain ? activeDrain.then(() => self._drain()) : self._drain();
```

Една патека со свесност, четири без.

**Анализа на достижност — потесна отколку што изгледа.** Запис ставен во нов синџир
додека тече празнење не влегува во веќе прочитаното множество. Но опоравувањето е
густо: `ack`, `nack`, секој `wakeup` тајмер и `online` настанот повикуваат ново
празнење, а тоа презема **сите** подготвени синџири, не само својот. Значи
заглавување бара празнење што завршува со **нула** преземени записи **и** нула
wakeup-ови (значи ниту еден тајмер) **и** новиот запис да стигне точно во тој прозорец.
Тогаш редицата чека до следниот надворешен поттик.

Заведено како 🟡 зашто последицата е одложена испорака во тесен прозорец, не губење —
но асиметријата меѓу петте повикувачи е реална и е фиксирана само на едното место.

## Затечена состојба

**Ова е единствената компонента чија основна логика е целосно одвоена од
прелистувачот.** `claimQueueHeads` и `remapQueueEntries` се чисти и извезени;
`QueueStorage` ги прима `indexedDB`, `IDBKeyRange`, `now` и `uuid` однадвор. Спореди
`ln-editor` (659 линии, нула модел, нула тест) и `ln-translations` (280 линии, нула
модел). Обрасецот постои и е применет најдобро токму таму каде е најтешко.

**`ln-api-queue` нема `-dev.scss`.** Единствената компонента во слој 4 без дев
афорданс, и единствената чиј најверојатен авторски промашај — редица без `id` внатре
во координатор без `id` — нема ниту еден сигнал.

**Idempotency гаранцијата зависи од заглавје што серверот можеби не го гледа.**
`ln-api-queue` го произведува стабилниот клуч правилно (`:130`); `ln-api-connector:85`
го праќа како `X-Idempotency-Key`, а неговото README документира `Idempotency-Key`
(наод AC2). Значи повторното праќање по истек на закуп (`claimQueueHeads:47-49`) —
механизам што оваа компонента го имплементира точно — се потпира на договор што е
скршен еден слој подолу.

Конзолен излез: еден `console.warn` (гејтиран) и два `console.error` (негејтирани,
QU6). Inline стил: нула. `createElement`: нула. Зашиен кориснички текст: нула.

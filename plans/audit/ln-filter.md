# Аудит — ln-filter

2026-09-11 · Опсег: `src/ln-filter.js` (380), `src/filter-model.js` (59), `README.md` (128), schema · Итерација 38/50

## Вердикт

Прва компонента во кампањата чиј механизам за криење се испорачува **со неа** —
`[data-ln-filter-hide="true"] { display: none; }` живее во ко-лоциран SCSS, не во
темата, па SYS-7 овде не важи. Но `destroy()` во режимот за табели брише под клуч што
никогаш не може да се совпадне со оној под кој запишал, и редовите остануваат скриени
засекогаш.

## Што е добро

**Криењето патува со компонентата.** `ln-filter.scss`:

```scss
[data-ln-filter-hide="true"] {
	display: none;
}
```

Три реда во ко-лоциран фајл, не во `theme/utilities/`. Значи консумент со core-only
CSS добива работен филтер. Тоа е првиот случај во кампањата каде компонента што крие
елементи го носи и правилото — `ln-tabs` (TB1), `ln-validate` (V4) и
`ln-external-links` (EL1) сите зависат од `.hidden` / `.sr-only` што core бандлот не
ги повлекува.

**Три извора за враќање состојба, со изречна претпочитаност** (`:98-136`): hash
(`:100-111`) → `data-ln-persist` (`:113-123`) → авторски `checked` (`:125-136`).
`restored` знаменцето гарантира дека само првиот што успее победува. Ниту една друга
компонента во кампањата нема толку јасно подредена каскада за обновување.

**`queueBoot` за рендерот при обновување** (`:105`, `:117`, `:129`) — обновената
состојба не испраќа настан пред портата за подигање да се отвори, па координатор што
сè уште не е конструиран не го пропушта.

**Диференцијална порта пред секој настан** (`:210-215`):

```js
const changed = !prev
	|| prev.key !== active.key
	|| arraysDiffer(prev.values, active.values);
if (!changed) return;
```

Кликање на веќе избрана опција не произведува настан. `_lastSnapshot` е вистинска
instance состојба, не огледало на атрибут.

**`createBatcher` ги спојува рендерите** (`:73-75`) — промена на пет чекбокса во еден
tick дава еден рендер.

**`matchesFilterValues` доаѓа од `ln-core`** (`:1`), делен со `ln-data-store`
(`filter-model.js:1` го увезува директно од `ln-core/matching.js`). Два консумента,
еден примитив — 2-Consumer правилото испочитувано, за разлика од `unwrapEnvelope`
(CD4) и CSRF барањето (U4).

**`filter-model.js` е чист и цел** — три извоза, сите три увезени (`:2`) и повикани
(`:35`, `:213`, `:316`).

**`destroy()` има гард за идемпотентност** (`:328`) — за разлика од `ln-data-store`
(DS4).

## Наоди

### 🔴 FL1 — `destroy()` во режим за табели брише под погрешен клуч

**Каде:** `:337` наспроти `:292`

Записот во споделената мапа користи **изведениот** клуч:

```js
// _filterTableRows:292
const key = active.key || (this.dom.getAttribute('data-ln-filter-key') || 'col' + this.colIndex);
…
filters[key] = { col: this.colIndex, values: values.slice() };
```

`active.key` доаѓа од `deriveActiveFilters` (`filter-model.js:52`), кое го зема
`data-ln-filter-key` на **првиот `<input>`**. Во документираниот маркап тоа е секогаш
поставено.

Бришењето користи само атрибутот на **хостот**:

```js
// destroy:337
const key = this.dom.getAttribute('data-ln-filter-key') || 'col' + this.colIndex;
if (key && filters[key]) delete filters[key];
```

Сопствениот пример на README-то (`:44-47`) го покажува расчекорот:

```html
<nav id="dept-filter" data-ln-filter="users-table" data-ln-filter-col="2" data-ln-persist>
  <label><input type="checkbox" data-ln-filter-key="dept" data-ln-filter-reset checked> All Departments</label>
  <label><input type="checkbox" data-ln-filter-key="dept" data-ln-filter-value="Engineering"> Engineering</label>
```

Хостот `<nav>` **нема** `data-ln-filter-key` — атрибутот живее исклучиво на
инпутите, и `ln-filter-dev.scss` правило 2 го проверува токму таму.

Значи:

| | клуч |
|---|---|
| `_filterTableRows` запишува | `"dept"` |
| `destroy()` брише | `"col2"` |

Никогаш не се совпаѓаат. Последиците:

1. **Записот останува во `_tableFilters`.** `WeakMap`-от е клучиран по `<table>`, па
   додека табелата е во DOM, филтерот на уништената компонента останува активен.
2. **Редовите остануваат скриени.** `evaluateRowFilters` (`filter-model.js:24-37`) го
   чита и понатаму, па секој следен рендер од **друг** филтер врз истата табела
   повторно ги крие истите редови — по правило што веќе нема контрола.
3. **`Object.keys(filters).length === 0` никогаш не станува точно** (`:339`), па
   `_tableFilters.delete(table)` не се извршува.

**Достижност:** секој `data-ln-filter-col` филтер што поминува низ `destroy()`.
README:94-119 го документира точно тој облик — филтер за колона внатре во popover во
`<th>` — што значи дека секое пре-рендерирање на заглавјето на табелата го уништува.

### 🟠 FL2 — `destroy()` не го брише `data-ln-filter-hide` од целта

**Каде:** `:327-354` наспроти `:277`

Во стандардниот режим (без `data-ln-filter-col`) `_render` пишува
`data-ln-filter-hide="true"` врз децата на целта (`:277`). `destroy()` не ја допира
целта воопшто — единственото чистење што го прави е за `_tableFilters` (`:331-342`,
и тоа со погрешен клуч, FL1).

Значи уништен филтер остава дел од списокот трајно скриен, а ко-лоцираниот SCSS го
прави тоа буквално невидливо. Ниту еден друг механизам не го брише атрибутот освен
следниот `_render` на **истата** инстанца — која веќе не постои.

Ист облик како SYS-9 (`destroy()` остава ARIA на хостот), но со потешка последица:
таму останува атрибут што ништо не чита, овде останува атрибут што CSS го спроведува.

### 🟠 FL3 — Режимот за табели филтрира по прикажан текст

**Каде:** `:313` и `filter-model.js:31`

```js
for (let c = 0; c < row.cells.length; c++) {
	cellValuesByCol[c] = row.cells[c].textContent.trim();
}
```

`mindset.md:103-105` го именува токму овој избор како разликата меѓу Ashlar и
мејнстримот, и во истата реченица го именува **атрибутот на оваа компонента**:

> **Mainstream way:** Filter and sort read `td.textContent` — whatever the display
> layer rendered.
> **Ashlar way:** `data-ln-value` on cells and **`data-ln-filter-value` on checkboxes**
> carry machine values. `td.textContent` is presentation only. **Sorting and filtering
> never read formatted text.**

`ln-core.readValue` постои точно за тоа (`data-ln-value`, инаку текст) и се користи од
`ln-table` за сортирање — овде не се вика.

Ова не е пропуст: README:16 го изнесува како функција — *„filters plain HTML `<table>`
rows by **column cell text**"*. Значи договорот на компонентата и доктрината си
противречат директно.

**Практичната последица** е видлива во постоечкиот маркап на репото:
`demo/admin/src/pages/table.html:176` носи
`<td data-ln-value="1499" data-ln-number class="numeric">1499</td>`. По иницијализација
`ln-number` го форматира текстот во `1,499` (или `1.499` по локале), а
`data-ln-value` останува `1499`. Филтер по таа колона споредува со форматираниот
стринг — значи вредноста за филтрирање се менува со јазикот на страницата.

### 🟠 FL4 — Истиот настан се испраќа двапати и обата буклаат

**Каде:** `:225-233`

```js
// 1. Dispatch on this.dom (Control Host) -> bubbles to ln-table-coordinator
dispatch(self.dom, 'ln-filter:change', detail);

// 2. Dispatch cancelable on target (State/Data Host) -> bubbles to ln-data-store / ln-table
if (target && target !== self.dom) {
	const evt = dispatchCancelable(target, 'ln-filter:change', detail);
	if (evt.defaultPrevented) defaultPrevented = true;
}
```

Дека `ln-filter` е единствената компонента што испраќа cancelable настан **кон
целта** наместо кон себе е **позната и одложена** ставка — не се брои како нов наод.

Новото е последицата од тоа што обата испраќања го носат **истото име** и обата
буклаат (`dispatch` и `dispatchCancelable` секогаш поставуваат `bubbles: true`):

Секој предок што ги содржи и контролниот хост и целта прима `ln-filter:change`
**двапати**, со идентичен `detail`. Тоа е вообичаениот распоред — README:94-119 го
покажува филтерот и табелата внатре во ист контејнер, а `ln-table-coordinator`
слуша на предок.

`ln-data-store`-овиот ракувач (`ln-data-store.js:300-317`) има no-op гард што ја
споредува претходната листа вредности, па вториот настан завршува тивко ✅ — но тоа е
случајна одбрана во една компонента, не својство на договорот. Координатор што брои
промени или логира ќе види дупло.

### 🟠 FL5 — Само hash е реактивен; целта и колоната се читаат еднаш, без афорданс

**Каде:** `:58`, `:61-62`, `:376-379`

```js
this.targetId = dom.getAttribute(DOM_SELECTOR);
const colAttr = dom.getAttribute(COL_ATTR);
this.colIndex = colAttr !== null ? parseInt(colAttr, 10) : null;
```

```js
registerComponent(DOM_SELECTOR, DOM_ATTRIBUTE, _component, 'ln-filter', {
	extraAttributes: [HASH_ATTR],
	onAttributeChange: _syncAttribute
});
```

`_syncAttribute` (`:358-372`) обработува **само** `data-ln-hash`. Значи:

- промена на `data-ln-filter` (целниот id) → инстанцата и понатаму филтрира по
  стариот id
- промена на `data-ln-filter-col` → и понатаму се чита старата колона

И двете се тивки. `data-ln-filter` дури е самиот селектор на компонентата, па неговата
мутација поминува низ гранка (В) на споделениот обсервер и завршува во
`_syncAttribute`, кој ја игнорира.

`ln-data-store` го реши истиот проблем еден слој погоре — `_markFrozen` (`:917-919`)
плус дев правило плус запис во схемата за атрибут што навистина не смее да се менува.
Тука не постои ниту едно од трите: атрибутите изгледаат како да важат, а не важат.

### 🟡 FL6 — Нема `ln-filter:destroyed`

**Каде:** `:327-354`

Компонентата испраќа `ln-filter:change` и `ln-filter:reset`, и ниту еден настан при
уништување. Секоја друга компонента во слоевите 3 и 4 го има својот
(`ln-form`, `ln-number`, `ln-upload`, `ln-autosave`, `ln-api-*`, `ln-data-store`).

Заедно со FL1 и FL2 тоа значи дека координаторот што држи евиденција за активни
филтри нема од што да дознае дека еден повеќе не постои — а состојбата што тој филтер
ја оставил (скриени редови, запис во `_tableFilters`) сè уште делува.

## Затечена состојба

**Cancelable-кон-целта отстапувањето е познато и одложено.** `:231` испраќа
`dispatchCancelable` кон **целниот** елемент наместо кон сопствениот хост — единствената
компонента во библиотеката што го прави тоа. Заведено е како познато отстапување и
**не се брои како нов наод**. Она што излезе овде е неговата втора последица —
двојното буклање под исто име (FL4) — која е независна од прашањето кон кого се
испраќа.

**`INIT_ATTR` багот е решен** (`6e768bc`) и не се појавува во тековниот извор ✅.

**`data-ln-filter-col` наспроти `data-ln-table-filter-col`.** README:128 носи Pitfall
што ја објаснува разликата — првиот е за самостоен филтер врз обичен `<table>`,
вториот за `ln-table`. Тоа е внимателна документација на вистинска замка во
именувањето, и ќе се провери од другата страна во **#42 ln-table**.

Конзолен излез: **нула** — единствената компонента во слој 4-5 досега без ниту еден
`console.*`. Целата дијагностика е во `ln-filter-dev.scss`, што е патеката на
`mindset.md:133`. Inline стил: нула. `createElement`: нула. Зашиен кориснички текст:
нула.

# Аудит — ln-options

2026-09-10 · Опсег: `src/ln-options.js` (74), `README.md` (66), schema · Итерација 7/50

## Вердикт

Уште еден чист event client. Кодот е точен; наодите се дека `<select>`-от може
тивко да ја смени вредноста на формата без никој да дознае, и дека README-то
самото си противречи во реченицата со која го оправдува `createElement`.

## Што е добро

**Зачувувањето на избраното е мислено.** `:36` го снима `dom.value` пред
преградбата, `:56-62` го враќа ако сè уште постои. Мнозинството имплементации го
испуштаат ова и корисникот го губи изборот на секој refresh.

**Placeholder-от преживува.** `:41` брише само `option.value !== ''`, па
`<option value="">All tenants</option>` останува. Документирано.

**Правилен изворен пат во Internals** — *„Source: `components/ln-options/src/ln-options.js`"*.
Единствената од петте компоненти во овој слој што покажува на `src/` наместо на
компајлираниот bundle.

**Нула зависност од `ln-data-store`** — податоците доаѓаат исклучиво преку
`ln-options:set-data`, а координаторот испорачува веќе декорирани записи, што
дозволува `data-ln-options-label` да сочи presenter-поле.

## Наоди

### 🟠 O1 — Изборот може тивко да се смени без настан

**Каде:** `:56-62`

```js
const opts = dom.options;
for (let i = 0; i < opts.length; i++) {
    if (opts[i].value === prev) { dom.value = prev; break; }
}
```

Ако `prev` **повеќе не постои** во освежените податоци, јамката не прави ништо —
а `<select>`-от веќе паднал на првата достапна опција при преградбата (`:39-53`).
Резултат: полето на формата има **нова вредност**, различна од онаа што корисникот
ја избрал, и:

- нема `change` настан,
- нема `input` настан,
- нема `ln-options:*` известување.

`ln-validate`, `ln-autosave` и auto-submit-от на `ln-form` не дознаваат. Корисник
што избрал наемник кој во меѓувреме е избришан ќе поднесе форма со **друг**
наемник, без ниту еден визуелен сигнал.

**Достижност:** секоја мутација на store-от што вади запис. README-то самото вели
дека координаторот пре-сервира на `deleted`.

**Спореди:** `ln-slug` испраќа синтетички `input` (`ln-slug.js:61`) токму за да ги
разбуди истите зависни компоненти при програмска промена на вредност. Тука не.

### 🟡 O2 — README си противречи во иста реченица

`README.md` §`<option>` creation:

> **The one sanctioned `document.createElement` case in the library** (mirrors
> `ln-table`'s select-all checkbox)

„Единствениот случај" и „го огледува ln-table" не можат да важат заедно — тоа се
два случаја. Плус, доктринарниот исклучок што го најдов при заземјувањето именува
**`ln-confirm`** како микро-компонентата со дозволен `createElement`. Три
различни множества исклучоци, ниту едно не се повикува на друго:

| извор | што именува како исклучок |
|---|---|
| DOCTRINE §4 / mindset #1, #12 | `ln-confirm` |
| `ln-options/README.md` | себеси + `ln-table` select-all |

Исклучокот тука е разумен — нативен `<option>` носи само `value` и текст, па
`<template>` би додал церемонија за две доделувања. Наодот е дека исклучоците
живеат во READMEs наместо во доктрината, па никој не знае колку ги има.

### 🟡 O3 — Небришењето важи само за празна вредност, недокументирано

`:41` — `if (existing[i].value !== '')` брише. Значи авторски напишана опција со
**непразна** вредност, на пр. `<option value="all">Сите</option>`, се брише на
првата испорака.

README-то ветува *„The placeholder `<option value="">` is preserved"*, што е точно —
но не кажува дека тоа е **единствениот** зачуван облик.

### 🟡 O4 — Временска ознака „v1"

Истата ознака како во `ln-slug` S4 и `ln-stat` ST3.

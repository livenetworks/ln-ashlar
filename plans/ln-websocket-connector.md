# ln-websocket-connector — live push transport

**Rulings (user, 2026-09-26):**
- A separate component. `ln-api-connector` does not change.
- Two demo examples: **(1)** REST + socket — `ln-api-connector` reads and writes, the socket only
  pushes changes; **(2)** socket alone — reads, writes and pushes.
- Connection status (`connecting` / `connected` / `disconnected`) is **private JS state announced by
  events**, never an attribute (`DOCTRINE.md` §3, "Attributes Are Set From Outside"). An explicit
  command from outside is allowed: `connect` / `disconnect`.
- On an unexpected drop the socket reconnects by itself and a catch-up sync fetches what was missed.
- A PHP mock generates random data for the demo.

**Why now:** no push transport exists — zero `WebSocket` / `EventSource` in `components/*/src`;
`ln-couchdb-connector` polls `_changes?feed=normal`. The coordinator already half-expects this
component: it selects `[data-ln-websocket-connector]` (`ln-data-coordinator.js:262`) and maps its
namespace (`:120`), but does not listen to its responses (`:115`) or take its instance (`:270`).

---

## A. Component — `components/ln-websocket-connector/`

`src/ln-websocket-connector.js`, `README.md`; schema and bundle are generated by the build.
Skeleton follows `ln-couchdb-connector` (IIFE, `registerComponent`, `ATTRIBUTES`, `defineAttrs`).

```html
<div data-ln-websocket-connector="connect" data-ln-websocket-connector-url="ws://localhost:8090"></div>
```

**Attributes** (host only, both settable from outside):

| Attribute | Type | Effect |
|---|---|---|
| `data-ln-websocket-connector` | enum `connect` \| `disconnect`, fallback `connect` | open / close the socket |
| `data-ln-websocket-connector-url` | string | on change: close and reopen on the new URL |

**Private state:** `_status` (`connecting` \| `connected` \| `disconnected`), the `WebSocket`,
the pending-reply map keyed by `ref`, the held-request list, the reconnect timer.

**Emits** (bubbling, on host):
- `:connecting { url, attempt }`, `:connected { url }`, `:disconnected { url, code, reason, willReconnect }`
- `:fetched`, `:created`, `:updated`, `:deleted`, `:bulk-deleted`, `:error` — same detail shapes as
  `ln-api-connector` / `ln-couchdb-connector` (`meta` echoed unchanged).

**Listens** (own namespace only — no `ln-api-connector:*` alias, per the no-aliases ruling):
`:request-sync`, `:request-query`, `:request-create`, `:request-update`, `:request-delete`,
`:request-bulk-delete`.

**Requests while not connected:** held while the command is `connect` (initial connect or between
reconnect attempts) and flushed in order on open. On `disconnect` or `destroy()`, held requests and
requests awaiting a reply fail with `:error { status: 0 }`; a socket drop fails the awaiting ones the
same way. Status 0 is transient in the coordinator's policy (`:715`) — local data is never deleted.

**Reconnect:** unexpected close while the command is `connect` → retry after 1 s, doubling, capped
at 30 s; reset on a successful open.

**`destroy()`:** close the socket, clear the timer, fail held/pending requests, remove listeners,
delete the instance refs (`DOCTRINE.md` §5).

## B. Wire protocol — JSON text frames

**Client → server:** `{ "ref": "<uuid>", "type": "<type>", ...payload }`

| type | payload (from the request event detail) |
|---|---|
| `sync` | `since` |
| `query` | `query` (`search`, `filters`, `sort`, `offset`, `limit`) |
| `create` | `data`, `idempotencyKey` |
| `update` | `id`, `data`, `expected_version`, `idempotencyKey` |
| `delete` | `id`, `idempotencyKey` |
| `bulk-delete` | `ids`, `idempotencyKey` |

**Server reply:** `{ "ref", "ok": true, "content", "message" }` or
`{ "ref", "ok": false, "status", "error", "data" }`. `{message, content}` mirrors the REST envelope.
`content` per type: sync → `{ data, deleted, synced_at }`; query → `{ data, total, filtered }`;
create/update → the record; delete/bulk-delete → the response.

**Server push (no `ref`):** `{ "type": "changes", "data": [...], "deleted": [...], "synced_at": ... }`
→ `:fetched { data: { data, deleted, synced_at }, since: null, meta: null }`. With no `meta.kind`
the coordinator hands it to `store.applySync` (`:592`) — the path CouchDB sync already uses.

`synced_at` must be the same token as the REST delta `since` — in example (1) a push advances the
store's `lastSyncedAt`, which the next REST sync sends. That is the server's contract; the mock
uses one shared change counter.

## C. Coordinator — `components/ln-data-coordinator/src/ln-data-coordinator.js`

1. `:115` — add `'ln-websocket-connector'` to `CONNECTOR_RESPONSE_NAMESPACES`.
2. `:262` `findChildren` — the request connector is `[data-ln-api-connector], [data-ln-couchdb-connector]`
   if present, else `[data-ln-websocket-connector]`. So in (1) requests go to REST and the socket only
   pushes; in (2) the socket takes requests too.
3. `:270` — add `|| connectorEl.lnWebsocketConnector`.
4. New listener `ln-websocket-connector:connected` → catch-up `store.forceSync()` under the same
   guards as `storeInitialized` (`:774`). In (1) that sync goes over REST, in (2) over the socket.
   Removed in `destroy()`.

The coordinator does not render connection status — that is page wiring (section E).

## D. PHP mock — `demo/websocket/ws-mock.php`

`php demo/websocket/ws-mock.php [port]` (default 8090). Pure PHP (`stream_socket_server` +
`stream_select`), no Composer. One process, one in-memory dataset of random tasks
(`id`, `title`, `status`, `priority`, `assignee`, `updated_at`). The same port serves:

- **WebSocket** (`Upgrade: websocket`): handshake, masked client frames in, text frames out,
  ping/pong/close; answers every protocol type from section B.
- **HTTP** for example (1), the routes `ln-api-connector` calls: `GET /tasks[?since=&search=&offset=&limit=&sort_by=&sort_dir=]`
  → `{ data, deleted, synced_at, total, filtered }`; `POST /tasks`; `PUT /tasks/{id}`;
  `DELETE /tasks/{id}`; `DELETE /tasks/bulk-delete`. CORS including `OPTIONS` preflight.

Every ~3 s a random change (mostly updates, sometimes create/delete) is broadcast as `changes` to
every socket. Every mutation, REST or socket, is broadcast too — a second tab sees the first tab's
writes. `synced_at` is a monotonic change counter; deletions are kept as tombstones for the delta.

The public demo server is pull-only, so the mock runs locally; the page says how to start it.

## E. Demo — `demo/admin/src/pages/websocket-connector.html`

Two sections, each a `ln-data-coordinator` with its own `ln-data-store` (distinct names) and a
data-driven `ln-table`:
1. `ln-api-connector` (`http://localhost:8090`, path `tasks`) + `ln-websocket-connector`.
2. `ln-websocket-connector` alone.

Each section has a status chip and a connect/disconnect button. A small page script
(`demo/admin/src/websocket-demo.js`, added to the copy list in `build-pages.mjs:19`) listens to
`:connecting` / `:connected` / `:disconnected` and writes an app-owned `data-status` on the chip
(app state stays out of `data-ln-*`); the chip colours live in the admin SCSS. The button flips
the host attribute value. Nav entry in `shell.html:194`, after CouchDB Connector. Compiled page
`demo/admin/websocket-connector.html` is committed (deploy is pull-only).

2. Reconnect timing 1 s → 30 s.
3. `query` over the socket in (2) — needed because a store with no cache answers reads remotely
   (`data-read-policy.js:20`, `canServe` false until the first sync).
4. Status rendering only in page wiring, not in `ln-data-coordinator`.
